# Code-first clip play stays on AnimationTree

Scripts need Animancer-like Play/fade without a Unity PlayableGraph. We decided any such surface is an API on the existing **AnimationTree** Unique — not a new playback attachment, not a revival of AnimationPlayer.Play, and not a third blend-specification producer beside Player and Tree. Clip Bindings, Fire slot, Sync Group, Edit preview, and Pipeline exclusivity stay on that one tree. **Clip Play** addresses a **Clip Binding** logical name, not a StateMachine state name and not an AnimationClip GUID. **Travel** / **Start** remain the state-name APIs (including BlendSpace states). Clip Play **replaces the tree base** with that one clip; it is not a Fire-slot insert and not Add2. It does not auto-return to the StateMachine; after the last key the pose holds that key and the override stays until Travel / Start. While a **Clip Play override** is set, authored StateMachine transitions do not auto-Travel; the current state name is remembered and not sampled. Fire slot and Add2 keep their current stacking: Fire exclusively samples while active, then the override is base again; Add2 still applies; Fire does not clear the override; the Clip Play clock keeps advancing during Fire. **Clip Play v1 is a hard cut** (no fade parameter); snapshot/mixer fade and per-edge fade stay a follow-up. A later Clip Play always restarts the named clip at 0 (same name included) and replaces the previous override; no queue. Clip Play **fails with no mutation** on empty name, missing Clip Binding, or inactive tree (no auto-activate). **Animation Window** v1 has no Clip Play control; **Stop** (and rebind Stop) still clears a Clip Play override like Fire. Clip Play override is **not serialized** (not scene, not Tree Asset instance override, not Document History). **v1 ship bar:** AnimationTree runtime + C-ABI + Blunder.Api + engine tests — not fade, not unified BlendSpec, not Window chrome, not Canvas, not a DogWalk Behaviour Done bar.

**Status:** accepted

**Considered options:** a new Animancer Unique beside or instead of AnimationTree (rejected — third sample path, forks Edit/Sync/Stepped); engine-only unified BlendSpec with no script Play this effort (rejected as the goal of the work); Clip Play as faded Travel by state name (rejected — BlendSpace states and unbound clips such as Hit would not be playable); one overloaded name that means state or clip (rejected — Idle-as-state vs Idle-as-binding collides); Clip Play as Fire-slot OneShot with fade (rejected — RequestOneShot already returns to base); Clip Play as a second additive layer (rejected — Add2 already owns overlay); auto-Travel during Clip Play override (rejected — speed/condition edges would cancel Hit); wrapping Clip Play via an AnimationClip loop field (rejected — Loop is not a clip asset flag); auto-clear override at clip end (rejected — that is OneShot); skipping Fire or Add2 during Clip Play override (rejected — extra exclusive mode; Sync Group must still Fire); Clip Play v1 fade via Player two-slot or unified BlendSpec mixer (rejected — Crossfade retired; BlendSpec unification is a separate follow-up); snapshot Local Pose fade in v1 (deferred with per-edge fade); queuing Clip Play or treating same-name Play as a no-op (rejected — Fire-like hard cut from 0); latching Clip Play on an inactive tree or unbound name (rejected — false success; Sync Fire already fails inactive members); Animation Window Clip Play chrome in v1 (deferred — Fire remains the Window insert); serializing Clip Play override (rejected — session like Fire occupancy); holding v1 on unified BlendSpec, fade, Window chrome, Canvas, or DogWalk content Play (rejected — runtime API + tests are the slice).
